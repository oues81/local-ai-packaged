3. If discovering and orchestrating external ACP agents:
   - Explain that the Devin Desktop ACP registry lives at `~/.windsurf/acp/registry.json` and lists available ACP agents with their launch commands and metadata.

   - The `acpRegistry` field in `clients.json` (devin client only) provides declarative metadata about which ACP agents ACOS should discover and orchestrate. Each entry has `id`, `enabled`, and `readsProjectMcp`.

4. Dual role of ACOS:
   - **ACOS as an ACP agent**: ACOS registers itself in the ACP registry via `agent.json` and serves through the `acp-serve` binary. The IDE launches ACOS, sends `session/new`, and interacts via `session/prompt`.
   - **ACOS as an ACP orchestrator**: ACOS reads `acpRegistry` in `clients.json`, discovers agents from `~/.windsurf/acp/registry.json`, and dispatches work to them via Agent-Waves ACP lanes. The MCP launcher bridge reads canonical per-project MCP projections (e.g., `.mcp.json`, `.devin/config.json`) at runtime to provide per-project isolation without creating divergent configuration.

## Wave orchestration

ACOS supports four execution modes for multi-agent wave dispatch:

- **acp-ide**: The IDE's agent client manages sub-agents via the ACP protocol. ACOS delegates to the
  IDE's native ACP session management.
- **acp-headless**: ACOS opens ACP sessions programmatically (`acp-orchestrator --mode acp-headless`),
  sending `session/new` with `mcpServers` and `cwd`, then `session/prompt` with each lane's mission.
- **cli-headless**: ACOS spawns CLI binaries (`devin.exe`, `claude`, `kilocode`, etc.) as detached
  background processes with `--prompt-file` and `--export` (`acos-wave-dispatch --mode cli-headless`).
- **cli-interactive**: ACOS launches visible terminal panes with each lane in its own pane. On Windows: `cmd /c start "" wt.exe -w new new-tab ... ; split-pane ...` (wt.exe is an App Execution Alias — `start ""` is required for a visible window from non-interactive contexts). Each lane gets a wrapper .js (JSON-serialized command, stdio:'inherit') launched via `cmd /k node wrapper.js`. On Linux/WSL: tmux new-session + new-window with wrapper .js per lane. (`acos-wave-dispatch --mode cli-interactive`).

### Wave-config format

The wave-config (`wave-config.json`) drives all four modes. It is validated against
`schemas/wave-config.json` and contains:

- `waveId`: `WAVE-<cycle>-<type>` (e.g. `WAVE-001-fix`)
- `waveType`: `fix | diagnose | validate | ship`
- `reportsDir`, `projectRoot`, `gitBranch`: paths and branch for worktree isolation
- `mode`: one of the four execution modes above
- `lanes[]`: each lane has `lane` (A1, A2, ...), `role`, `client`, `worktree`, `worktreeBranch`,
  `promptTemplate`, `mission`, `files`, `tests`, `reportFile`, `statusFile`, and optional `mcpServers`

### New bins

- **`acos-wave-plan`**: Reads `specs/<feature-id>/tasks.md`, parses structured task fields (Files,
  Domain, Parallelizable, Lane, Depends on), groups tasks into non-overlapping lanes, and writes a
  validated `wave-config.json`. Usage: `acos-wave-plan --root . --spec <feature-id> --wave-type <type>`.
- **`acos-wave-dispatch`**: CLI runner that accepts a wave-config and dispatches lanes via CLI binaries
  (`--mode cli-headless` or `--mode cli-interactive`). Supports `--launch`, `--monitor`, `--dry-run`,
  `--cleanup`.
- **`acp-orchestrator`**: ACP runner that accepts a wave-config and dispatches lanes via ACP sessions
  (`--mode acp-headless` or `--mode acp-ide`). Supports `--launch`, `--monitor`, `--dry-run`.
