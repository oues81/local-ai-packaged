> **Bootstrap note**: If you are reading this as a projected skill but ACOS is
> not yet installed on the project (no `npx acos` available), see
> `docs/bootstrap.md` for the install + init snippet that must run first. This
> skill assumes ACOS is installed and `.ssot/` has been created by
> `acos init --adopt`.

Treat the user's accompanying text as the project objective. Minimize questions.

1. Inspect the repository, Git state, environment, manifests, and existing documentation.
2. If `.ssot/` already exists, stop this workflow and apply `project.resume` or `0660-sync` instead.
3. If any ACOS-related or agent-related files exist (e.g., `.claude/`, `.cursor/`, `.codex/`, `.devin/`, `.kilo/`, `.kilocode/`, `.opencode/`, `.agents/`, `.windsurf/`, `AGENTS.md`, `CLAUDE.md`, configs client, etc.), perform a pre-init audit **before** any mutation:
   - Read the existing files and classify them semantically: custom business rules, stale ACOS projections, client configs, unknown files.
   - Run `node scripts/audit/pre-init-audit.mjs --root .` to produce a deterministic inventory and risk report (`ACOS_PRE_INIT_AUDIT.md`).
   - Run `node scripts/audit/pre-init-audit.mjs --root . --migration-plan` to produce a structured draft migration plan (`ACOS_MIGRATION_PLAN.json`).
   - Compare your semantic analysis with the deterministic report and the draft plan; correct any discrepancies and refine the plan.
   - Decide what must be preserved, migrated into `.ssot/`, or left as-is.
4. If existing files are at risk of being overwritten by `acos init --adopt` or `acos --fix`:
   - Back them up to a safe location (e.g., `.acos/pre-init-backup/<timestamp>/` or a temporary Git branch).
   - Use the structured migration plan (`ACOS_MIGRATION_PLAN.json`) as a draft; write a human-readable migration plan (`ACOS_PRE_INIT_MIGRATION_PLAN.md`) documenting every preservation decision.
   - Present the plan to the user and pause for explicit approval before any mutation.
5. Detect the stack and derive setup, test, lint, build, and run commands from repository evidence.
6. Discover the configured shared infrastructure profile and reuse its Harbor, caches, and MCP management plane when available.
7. Initialize ACOS with `acos init --adopt` (only after approval).
8. Generate projections with `acos --fix`. The sync generates the full set of client surfaces declared in `clients.json`. New surfaces from the July 2026 audit:
   - **Devin**: `.devin/agents/*/AGENT.md` (custom subagents, experimental), `.agents/agents/*/AGENT.md` (shared standard). `.devin/rules/` is a native CLI surface — Devin CLI reads `.devin/rules/*.md` natively since v3000.x. `.devin-plugin/plugin.json` is fully ACOS-generated.
   - **Codex**: `.codex/rules/*.rules` (Starlark exec-policy rules). `.codex/skills/` is legacy — `.agents/skills/` is the primary skills location for Codex. `.codex-plugin/plugin.json` is fully ACOS-generated.
   - **Kilo**: `.kilo/plugin/acos-hooks.ts` (hooks via plugin system, DD-014). `.kilocode/` paths are legacy.
   - **OpenCode**: `.opencode/plugins/acos-hooks.ts` (hooks via plugin system, DD-014).
   - **Claude**: `.claude/workflows/*.js` (dynamic workflows, placeholder), `.claude/output-styles/*.md`. `.claude-plugin/plugin.json` is fully ACOS-generated.
   - **Cursor**: `.cursor/permissions.json`, `.cursor/cli.json`. `.cursor-plugin/plugin.json` is fully ACOS-generated.
   - **All clients**: plugin manifest directories (`.devin-plugin/`, `.codex-plugin/`, `.claude-plugin/`, `.cursor-plugin/`) are declared in `clients.json` and are fully ACOS-generated — the sync creates the directory and full ACOS-generated manifest.
9. Complete the ACOS context files under `.ssot/` without overwriting meaningful existing content.
10. **Prefix standardization for custom entrypoints** — before creating any custom entrypoint,
    classify the need:
    1. Check whether the need is already covered by an existing core category in
       `docs/specs/000-numbering-conventions/spec.md` — if yes, reuse or extend the core entrypoint,
       do not invent a new prefix.
    2. If the project declares or will declare `ecosystemParent`/`ecosystemChildren` in
       `.ssot/agents/clients.json`, and the need is shared across satellites, use a 13xx–14xx
       (`category: ecosystem`) entrypoint declared at the container level.
    3. Otherwise, use a 1500+ (`category: project`) entrypoint.
    4. Never use 0xx–12xx for a non-core need. Never use the core-reserved slots 500, 520, 530, or
       540 for project/ecosystem entrypoints.
    5. Record the classification decision alongside the entrypoint in `.ssot/agents/workflows.json`.
11. Record known facts, explicit assumptions, unresolved decisions, and the first executable milestone.
12. If the user provided a first objective, optionally create the first spec under `specs/<feature-id>/spec.md` using the template at `.ssot/agents/specs/spec-template.md`.
13. Reconcile an executable specification and implementation plan for the first milestone.
14. Present the plan and pause for one explicit user approval before implementation mutations.
15. After approval, execute and verify the approved milestone without requiring separate workflow invocations.
16. **Optional — MCPCO ecosystem-parent opt-in**: ask the operator whether this project uses MCPCO
    (the MCP Cycle Orchestrator). If yes:
    1. Copy the template profile from `templates/ssot/.ssot/mco-profile.json` to `.ssot/mco-profile.json`
       (the project's own copy). The operator may override `mcpEndpoint` with their MCO deployment URL and
       set `MCP_API_KEY` in `.env` if authentication is enabled.
    2. Add the `ecosystemParent` declaration to `.ssot/agents/clients.json`:
       `"ecosystemParent": {"path": "ecosystem-parents/mco"}`.
    Do NOT probe the network or attempt to connect to the MCO endpoint during init (REQ-009; DD-031).
    Init never fails because MCPCO is absent or unreachable.
17. Run ACOS validation and projection checks (`acos --validate`, `acos --check`), then persist status and handoff evidence.
18. Return only decisions that genuinely require the user, followed by the next concrete action.

Never invent dependencies, credentials, deployment targets, or product requirements.
